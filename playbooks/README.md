# Плейбуки: готовые схемы оптимизации по типу продукта

[← К содержанию](../README.md) · [Чек-листы](../checklists/README.md) · [Калькуляторы](../calculators/README.md)

Шесть типовых продуктов. Для каждого: где обычно утечка, порядок рычагов, ожидаемый результат, чего делать нельзя. Берите ближайший к своему и идите по шагам.

| Плейбук | Типичная утечка | Ожидаемый эффект |
|---|---|---|
| [1. Чат-поддержка](#плейбук-1-чат-поддержка) | шапка на каждом шаге, длинная история | в 4–6 раз |
| [2. RAG-поиск по документам](#плейбук-2-rag-поиск-по-документам) | контекст «на всякий случай» | в 3–5 раз |
| [3. Кодовый агент](#плейбук-3-кодовый-агент) | файлы целиком, шаги, полные ответы | в 3–8 раз |
| [4. Массовая разметка и классификация](#плейбук-4-массовая-разметка-и-классификация) | интерактивный тариф, длинные ответы | в 5–20 раз |
| [5. Обработка документов](#плейбук-5-обработка-документов) | вложения целиком, повторная обработка | в 4–10 раз |
| [6. Аналитический агент и отчёты](#плейбук-6-аналитический-агент-и-отчёты) | длинные цепочки шагов, размышления | в 2–4 раза |

---

## Плейбук 1. Чат-поддержка

**Профиль.** Интерактивный диалог, 3–8 ходов, инструменты (заказы, тарифы, база знаний), требование к вежливости и точности.

**Где утечка.** Системный промпт и схемы инструментов пересылаются на каждом ходе; история растёт; ответы длиннее, чем нужно в интерфейсе; база знаний целиком в шапке.

**Порядок работ.**

| Шаг | Действие | Эффект |
|---|---|---|
| 1 | Кэш на политику, схемы инструментов и стайлгайд; скользящая отметка на историю | −60…−80% входа |
| 2 | База знаний — из шапки в инструмент поиска, в шапке оставить оглавление | −30…−50% остатка |
| 3 | Ответы инструментов усечь: сводки вместо полных объектов | −20…−40% |
| 4 | Ограничить длину реплики: «не пересказывай вопрос, не перечисляй то, что видно в интерфейсе» | −30% выхода |
| 5 | Дешёвая модель на классификацию интента и компакцию, средняя на диалог | −10…−20% |
| 6 | Точный кэш ответов на справочные вопросы («как вернуть товар») | −10…−25% вызовов |
| 7 | Ночной батч на аналитику диалогов | −50% на этом слое |

**Чего не делать.** Не понижать модель на самом диалоге до шага 6 — качество общения самое заметное для пользователя. Не кэшировать ответы, зависящие от статуса заказа. Не сжимать историю на каждом ходе.

**Метрики приёмки.** `cache_hit_ratio` > 0,8; `out/in` < 0,12; `steps_per_task` 3–6; доля переспрашиваний не выросла; `pass_rate` канареечного набора не упал.

## Плейбук 2. RAG-поиск по документам

**Профиль.** Вопрос — поиск по корпусу — ответ со ссылками. Корпус от сотен до миллионов документов.

**Где утечка.** В контекст кладут 20 фрагментов «на всякий случай»; фрагменты слишком большие; переиндексация всего корпуса при каждом изменении; ответ цитирует целые абзацы вместо ссылок.

**Порядок работ.**

| Шаг | Действие | Эффект |
|---|---|---|
| 1 | Кэш на инструкцию и правила цитирования | −20…−40% входа |
| 2 | Сократить число фрагментов: измерить, сколько реально используется (обычно 3–5 из 20) | −50…−70% входа |
| 3 | Переранжирование дешёвой моделью: 20 кандидатов → 4 фрагмента | −30% и рост точности |
| 4 | Ответ: номера пунктов и ссылки вместо цитат целыми абзацами | −40…−80% выхода |
| 5 | Дельта-индексация по отпечатку содержимого | −90% на пайплайне индексации |
| 6 | Точный кэш ответов на частые вопросы плюс ночной предрасчёт топ-100 | −20…−40% вызовов |

**Чего не делать.** Не увеличивать число фрагментов «для надёжности» без замера: после 5–6 фрагментов точность обычно перестаёт расти, а цена растёт линейно. Не включать семантический кэш без измерения ложных попаданий.

**Метрики приёмки.** Число фрагментов в контексте; доля ответов с корректными ссылками (проверяется автоматически: цитата реально есть в источнике); `cost_per_success`.

## Плейбук 3. Кодовый агент

**Профиль.** Правки в репозитории, чтение файлов, запуск тестов, итерации до зелёного прогона.

**Где утечка.** Файлы читаются целиком; ответы содержат весь файл вместо диффа; много шагов; размышления на каждом шаге; повторное чтение одного и того же файла.

**Порядок работ.**

| Шаг | Действие | Эффект |
|---|---|---|
| 1 | Кэш на инструкции, стайлгайд, описание архитектуры проекта | −40…−60% входа |
| 2 | Чтение файлов по диапазонам строк и по символам, а не целиком; `grep` вместо загрузки | −50…−80% входа |
| 3 | Кэш прочитанных файлов внутри задачи (повторное чтение — бесплатно) | −15…−30% шагов |
| 4 | Формат правки — дифф или «строка: новое содержимое», не файл целиком | −70…−90% выхода |
| 5 | Бюджеты: шаги, деньги, время; критерий готовности «тесты зелёные» | обрезает хвост в разы |
| 6 | Размышления только на планировании и отладке, не на механических правках | −20…−40% выхода |
| 7 | Верхняя модель на планирование и сложную отладку, средняя на механику | −20…−40% |

**Чего не делать.** Не понижать модель на генерации кода без строгого набора тестов: цена ошибки в коде высокая, а ошибки бывают тонкими. Не отключать размышления на отладке.

**Метрики приёмки.** `steps_per_task`; доля задач, закрытых с первого прогона тестов; `out/in`; средний объём прочитанного на задачу.

## Плейбук 4. Массовая разметка и классификация

**Профиль.** Десятки и сотни тысяч однотипных задач: категории, теги, тональность, извлечение полей.

**Где утечка.** Интерактивный тариф вместо батча; верхняя модель там, где хватает дешёвой; развёрнутые ответы с объяснениями; повторная обработка неизменившихся записей.

**Порядок работ.**

| Шаг | Действие | Эффект |
|---|---|---|
| 1 | Строгий формат ответа: JSON по схеме, без объяснений | −70…−90% выхода |
| 2 | Batch API | −50% на всё |
| 3 | Одинаковая шапка на всю пачку: кэш работает внутри батча | −60…−80% входа |
| 4 | Дешёвая модель плюс контроль по схеме плюс эскалация неуверенных случаев | −60…−85% |
| 5 | Дельта-обработка по отпечатку содержимого | −80…−95% на повторных прогонах |
| 6 | Дедупликация одинаковых текстов до отправки | −5…−30% |
| 7 | Пробная пачка 200 записей, стоп-кран по доле сбоев | защита от сжигания бюджета |

**Чего не делать.** Не запускать полный прогон без пробной пачки. Не игнорировать эскалацию: 3–7% неуверенных случаев на дорогой модели почти не влияют на итоговую цену, но сильно влияют на качество.

**Метрики приёмки.** `cost_per_1000_items`; доля `needs_review`; `pass_rate` на размеченной вручную выборке из 200 записей; доля записей, дошедших до `done` с первой попытки.

**Ожидаемая экономика.** Комбинация «дешёвая модель + батч + кэш шапки + строгий формат» на типичной задаче даёт 10–20-кратное снижение против «верхняя модель интерактивно с объяснениями» при сопоставимом качестве. Это самый благодарный сценарий во всём гайде.

## Плейбук 5. Обработка документов

**Профиль.** PDF, сканы, договоры, счета. Извлечение полей, проверка условий, сводки.

**Где утечка.** Страницы отправляются изображениями там, где есть текстовый слой; документ целиком вместо нужных страниц; повторная обработка одного документа; полные объекты в ответах инструментов.

**Порядок работ.**

| Шаг | Действие | Эффект |
|---|---|---|
| 1 | Извлекать текстовый слой парсером; изображения — только там, где текста нет | −50…−90% входа |
| 2 | Нарезка на страницы и разделы, оглавление в шапке, модель запрашивает нужный раздел | −60…−85% входа |
| 3 | Кэш на инструкцию извлечения и схему полей | −20…−40% остатка |
| 4 | Строгая схема результата, никаких объяснений | −60…−80% выхода |
| 5 | Батч для архивов и плановых прогонов | −50% |
| 6 | Отпечаток документа: не обрабатывать повторно | −80…−95% на повторах |
| 7 | Дешёвая модель на простые формы, эскалация нестандартных | −40…−70% |

**Чего не делать.** Не отправлять сканы в высоком разрешении «для надёжности» без замера: часто среднее разрешение даёт то же качество распознавания за долю цены. Не пропускать валидацию извлечённых полей — дешёвая проверка ловит большую часть ошибок бесплатно.

**Метрики приёмки.** Стоимость обработки одного документа; точность по полям на размеченной выборке; доля документов, потребовавших ручной проверки.

## Плейбук 6. Аналитический агент и отчёты

**Профиль.** «Собери и объясни»: агент ходит по данным, считает, формирует отчёт. Длинные цепочки шагов, размышления, большие выгрузки.

**Где утечка.** Огромные выгрузки в контексте; много шагов; размышления на каждом; отчёт генерируется целиком при каждом обновлении.

**Порядок работ.**

| Шаг | Действие | Эффект |
|---|---|---|
| 1 | Агрегаты вместо сырых данных: считать SQL, а не моделью | −70…−95% входа |
| 2 | Кэш на инструкции, определения метрик, описание схемы данных | −30…−50% остатка |
| 3 | Бюджеты и критерий останова; параллельные независимые запросы в одном шаге | −30…−50% |
| 4 | Размышления — только на этапе планирования анализа | −20…−40% выхода |
| 5 | Батч для плановых отчётов, интерактив — только для ad-hoc | −50% на плановых |
| 6 | Инкрементальные отчёты: пересчитывать изменившиеся разделы | −60…−90% |
| 7 | Шаблон отчёта в коде, модель заполняет только содержательные поля | −40…−70% выхода |

**Чего не делать.** Не давать модели считать арифметику там, где это может сделать код: это и дороже, и менее надёжно. Не понижать модель на интерпретации данных — здесь как раз живёт ценность.

**Метрики приёмки.** `cost_per_report`; `steps_per_task`; доля отчётов, принятых без правок; расхождение чисел в отчёте с эталонным расчётом (должно быть нулевым).

## Как адаптировать плейбук под себя

1. Выберите ближайший профиль и **не выполняйте все шаги подряд** — сначала измерьте, какой из указанных источников утечки есть у вас.
2. Идите по шагам в указанном порядке: он выстроен от безопасного к рискованному.
3. После каждого шага прогоняйте набор тестов и записывайте пару «`cost_per_success` / `pass_rate`».
4. Остановитесь, когда цена задачи стала приемлемой. Оставшиеся шаги — задел на будущее, а не обязательная программа.
5. Зафиксируйте результат в репозитории: конфигурация, цифры, дата. Через квартал это единственный способ понять, что изменилось.
