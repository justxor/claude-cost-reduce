# code/ — рабочий код

[← К содержанию](../README.md)

Всё запускается без API-ключа: там, где нужен провайдер, используется заглушка или явный флаг `--live`. Ключ нужен только для `cache_probe.py --live` и `batch_runner.py --live`.

| Файл | Что делает | Ключ нужен |
|---|---|---|
| [cost_meter.py](cost_meter.py) | считает деньги по `usage`, бюджеты задачи, отчёт `cost_per_task / cost_per_success`, подсказки «идите в модуль N» | нет |
| [cache_probe.py](cache_probe.py) | offline-проверки стабильности префикса плюс диагноз по трём реальным запросам | только для `--live` |
| [router.py](router.py) | маршрутизация по классам задач, контроль качества, каскад с эскалацией, экономика каскада | нет |
| [batch_runner.py](batch_runner.py) | возобновляемый пакетный прогон: состояние, пробная пачка, стоп-кран, идемпотентная запись | только для `--live` |

## Быстрый старт

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python code/cost_meter.py     # сравнение пяти конфигураций на синтетике
python code/router.py         # маршрутизация и экономика каскада
python code/cache_probe.py    # проверка стабильности сборки промпта
python code/batch_runner.py   # пакетный прогон на заглушке
```

Каждый файл начинается с `_self_test()`: если он падает, значит вы изменили логику и сломали инвариант. Тест, который никогда не падал, — не тест, поэтому специально сломайте что-нибудь и убедитесь, что проверки краснеют.

## cost_meter.py

Ядро всего гайда: **без учёта денег в момент вызова оптимизация делается вслепую.**

Что важно понять из этого файла:

- `price()` считает четыре компонента отдельно: свежий вход, запись кэша, чтение кэша, выход. Именно эта раздельность позволяет увидеть, работает ли кэш.
- `price_naive()` считает, сколько стоил бы тот же вызов без кэша и батча. Разница — ваша честная экономия, а не «мы что-то внедрили».
- `CostMeter.report()` даёт `cost_per_task`, `cost_per_success`, `p95/median`, `cache_hit_ratio`, `out_in_ratio` и разбивку по сценариям.
- `CostMeter.warnings()` читает эти метрики и говорит, какой модуль гайда открыть.
- `Meter` и `Budget` реализуют четыре бюджета задачи: шаги, токены, деньги, время.

Демонстрация печатает таблицу пяти конфигураций. Ключевая строка — последняя: самая дешёвая конфигурация имеет худший `pass_rate`, и по `cost_per_success` она проигрывает. Это визуальное доказательство главного правила гайда.

## cache_probe.py

Половина этого файла работает без сети — и именно она находит большинство причин «кэш не работает»:

| Проверка | Что ловит |
|---|---|
| `check_deterministic` | кэшируемая часть зависит от вопроса пользователя |
| `check_broken_detected` | проверка самой проверки: таймстемп в шапке должен быть обнаружен |
| `check_marks_present` | отметки `cache_control` просто не проставлены |
| `check_variable_below` | изменчивое попало выше границы кэша |
| `check_prefix_size` | префикс короче минимального порога, отметка игнорируется |

Онлайн-часть делает три идентичных запроса и выдаёт диагноз словами: «кэш работает правильно», «кэш пишется на каждом запросе — ищите убийцу», «читается меньше половины записанного — опустите отметку», «кэш не задействован». Стоит центы.

**Как воспроизвести поломку специально:** `python code/cache_probe.py --live --broken` — в шапку добавляется таймстемп, и вы увидите `cache_creation` на каждом запросе. Полезно один раз увидеть своими глазами.

## router.py

Три вещи в одном файле:

1. **Правила маршрутизации** с обязательным `route_reason`. Без объяснения выбора отладка маршрутизации превращается в гадание, а дрейф маршрутизации — частая причина внезапного роста счёта.
2. **`QualityGate`** — дешёвый формальный контроль: обязательные поля, допустимые значения, диапазоны чисел, проверка цитаты в источнике, порог уверенности, уважение к `needs_review`. Каскад без такого контроля дороже, чем чистая дорогая модель.
3. **`economics()`** — расчёт, где `manual_cost` (цена провала) стоит первым по важности слагаемым. При цене ручной доработки 4 доллара конфигурация «только дешёвая модель» почти всегда самая дорогая.

Обратите внимание на правило `attempt > 0 -> уровень выше`: повтор той же моделью с тем же промптом почти наверняка даёт тот же провал за двойную цену.

## batch_runner.py

Каркас пакетной обработки, который не сгорит на 200 000 записях:

- состояние в SQLite: `pending / running / done / failed`, число попыток, отпечаток содержимого;
- **дельта-обработка**: запись с неизменившимся отпечатком `sha256(content + PROMPT_VERSION)` не обрабатывается повторно;
- **пробная пачка** перед большим прогоном;
- **стоп-кран** по доле сбоев: систематическая ошибка не превращается в 200 000 записей мусора;
- идемпотентная запись результатов по `custom_id`;
- валидация каждого результата по схеме перед сохранением.

Запуск без ключа проходит по заглушке и печатает сводку: сколько обработано, сколько пропущено дельтой, сколько ушло в ручной разбор, сколько стоило бы интерактивно и сколько батчем.

## Как встроить это в свой проект

1. Скопируйте `price()` и `CostMeter`, вынесите `PRICES` в конфиг с датой актуальности.
2. Оберните свой вызов модели так, чтобы после каждого ответа вызывался `record()` с `task_id` и `scenario`.
3. Добавьте `Budget` в агентный цикл и обработку `BudgetExceeded` как частичного результата.
4. Прогоните `cache_probe.py` на своей функции сборки промпта — замените `build_request()` на свою.
5. Возьмите `QualityGate` как основу контроля для каскада, но настройте проверки под **реальные** ошибки вашей дешёвой модели, а не под воображаемые.
6. Заведите `_self_test` в CI: он бесплатный и ловит поломки инвариантов учёта.

**Чего в этом коде сознательно нет:** сетевых ретраев, конкурентности, метрик в Prometheus, трассировки. Это каркас для понимания и адаптации, а не готовая библиотека. Ваша инфраструктура наверняка уже умеет большую часть этого — задача в том, чтобы деньги и `usage` доходили до неё в каждом вызове.
