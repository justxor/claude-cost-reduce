# 04. Управление выходными токенами: самый дорогой токен в системе

[← 03. Агентный цикл](../03-agent-loop/README.md) · [К содержанию](../README.md) · [Дальше: 05. Batch API →](../05-batch-api/README.md)

> **Главный вопрос модуля.** Сколько из того, что модель написала, пользователь или ваш код действительно прочитали?

Выходной токен стоит в 4–5 раз дороже входного. При этом именно выход почти никто не оптимизирует: контекст видно в коде, а длину ответа как будто определяет модель. Не определяет — определяете вы.

**Критерий приёмки:** `out/in` по логам меньше 0,15 для агентных сценариев и меньше 0,05 для извлечения данных; `max_tokens` выставлен осознанно для каждого типа запроса; доля ответов, обрезанных по лимиту (`stop_reason: max_tokens`), меньше 1%.

## 04.1 Почему выход дороже, чем кажется

Три причины, по которым выход бьёт по счёту сильнее ожиданий.

**Причина 1. Цена за токен.** Обычно в 4–5 раз выше входной. Сто лишних токенов на выходе стоят как четыреста-пятьсот на входе.

**Причина 2. Выход становится входом.** В диалоге и в агентном цикле сгенерированный ответ уходит в историю и переотправляется на каждом следующем шаге. Лишний абзац в шаге 2 оплачивается ещё девять раз, если впереди девять шагов. Это делает выход участником квадратичной формулы из [модуля 03](../03-agent-loop/README.md).

**Причина 3. Размышления считаются выходом.** Расширенные рассуждения — это выходные токены по полной цене, и их обычно не видно в интерфейсе, поэтому о них забывают. Модель может «подумать» на 3 000 токенов ради ответа в 40.

| Что оптимизируем | Экономия на 1 000 токенов (иллюстративно, тариф 3/15 $) | Влияние на историю |
|---|---|---|
| Входной контекст | 0,003 $ | нет |
| Выходной ответ | 0,015 $ | да, множится на число последующих шагов |
| Размышления | 0,015 $ | обычно нет, но платится каждый шаг заново |

Практический вывод: **начинайте с `out/in`.** Если это отношение больше 0,2, вы почти наверняка сэкономите больше на выходе, чем на любом сжатии контекста.

## 04.2 Формат вместо прозы

Главный приём модуля: не просите «объясни и ответь», просите **структуру**.

```python
# Плохо: 600-900 выходных токенов
"Проанализируй обращение и определи категорию, приоритет и нужна ли эскалация. Объясни решение."

# Хорошо: 40-60 выходных токенов
"Верни только JSON: {\"category\": один из [billing, tech, sales], \"priority\": 1-3, \"escalate\": bool}. Без пояснений."
```

Разница в 12 раз. И почти всегда качество классификации не меняется: объяснение писалось не для модели и не для пользователя, а «на всякий случай».

**Когда объяснение действительно нужно** — просите его отдельным полем с лимитом: `{"reason": "не более 15 слов"}`. Это сохраняет проверяемость решения и не даёт разрастись эссе.

| Приём | Формулировка | Типичная экономия |
|---|---|---|
| Строгий JSON по схеме | «Верни только JSON по схеме, без markdown и пояснений» | 60–90% |
| Ограничение словами | «Не более 40 слов» / «Одно предложение» | 30–70% |
| Только идентификаторы | «Верни id подходящих пунктов, а не их текст» | 80–95% |
| Запрет на пересказ | «Не повторяй вопрос и не пересказывай контекст» | 15–30% |
| Запрет вступлений | «Начинай сразу с ответа, без вводных фраз» | 5–15% |
| Ссылки вместо цитат | «Укажи номер пункта вместо цитирования» | 40–80% |
| Дельта вместо целого | «Верни только изменённые строки, а не весь файл» | 70–95% |

**Последний приём — самый сильный в коде-агентах.** Возврат полного файла на 800 строк вместо трёх изменённых — это тысячи выходных токенов на каждую правку. Формат «дельта» (номер строки плюс новое содержимое, либо патч) сокращает выход на порядок и заодно уменьшает шанс, что модель случайно перепишет то, что не просили.

## 04.3 Инструменты управления длиной

```python
resp = client.messages.create(
    model=MODEL,
    max_tokens=300,                  # жёсткий потолок, ставится по типу запроса
    stop_sequences=["\n\n---"],      # обрываем, когда пошла ненужная часть
    system=SYSTEM,
    messages=msgs,
)
if resp.stop_reason == "max_tokens":
    metrics.incr("truncated")        # обязательно считаем: это признак плохого лимита
```

| Инструмент | Что делает | Как выбрать значение |
|---|---|---|
| `max_tokens` | жёсткий потолок генерации | p99 длины успешных ответов из бейзлайна плюс 20% |
| `stop_sequences` | обрывает генерацию на маркере | если модель склонна добавлять «Дополнительно:» или разделитель |
| Структурированный вывод по схеме | делает формат обязательным, а не пожеланием | всегда, когда ответ потребляет код, а не человек |
| Префилл начала ответа | заставляет начать с `{` или с нужного слова, отсекая вступление | для JSON и коротких вердиктов |
| Разделение на два вызова | короткий вердикт сейчас, подробности по требованию | если подробности нужны в меньшинстве случаев |

**Про `max_tokens` есть тонкость.** Он не делает ответ короче — он его **обрезает**. Обрезанный JSON нельзя распарсить, и вы платите за мусор плюс за ретрай. Поэтому `max_tokens` — это защита от катастрофы, а не способ сокращения. Способ сокращения — формат и инструкция. Именно поэтому доля `stop_reason: max_tokens` должна быть меньше 1%: если она выше, ваш лимит режет полезные ответы.

**Приём «вердикт, потом подробности».** Вместо одного длинного ответа два вызова: первый возвращает решение в 20 токенов, второй (только если пользователь нажал «почему?») — объяснение. Если кнопку нажимают в 10% случаев, вы платите за объяснения в десять раз реже.

## 04.4 Размышления: когда они стоят своих денег

Расширенные размышления (thinking) — мощный инструмент качества и одновременно самый незаметный источник расходов, потому что их не видно в продукте.

| Тип задачи | Нужны ли размышления | Бюджет |
|---|---|---|
| Классификация, извлечение полей, маршрутизация | нет | выключить |
| Форматирование, перевод, короткий пересказ | нет | выключить |
| Многошаговая арифметика, финансовые расчёты | да | небольшой |
| Планирование действий агента, выбор стратегии | да | средний |
| Отладка сложной ошибки, доказательства, анализ противоречий | да | большой |
| Творческий текст | обычно нет | выключить или минимум |

**Метод подбора бюджета.** Возьмите набор тестов и прогоните на трёх уровнях: выключено, небольшой бюджет, большой. Получите таблицу «`pass_rate` против `cost_per_task`» и выберите точку, где рост качества выходит на плато. Почти всегда плато наступает раньше, чем вы ожидаете, — а платите вы за весь бюджет, а не за «столько, сколько понадобилось».

```
pass_rate
0,94 |                    ● большой бюджет (0,041 $)
0,93 |            ● средний (0,022 $)   ← точка выбора: плато началось
0,86 |    ● без размышлений (0,009 $)
     +-------------------------------------- cost_per_task
```

В этом примере средний бюджет даёт 99% качества большого за половину цены. Разница между 0,93 и 0,94 обычно не стоит удвоения счёта — но это решение продукта, а не инженера: иногда стоит.

**Тонкость про кэш и размышления.** Блоки размышлений попадают в историю диалога. Если вы их сохраняете, они увеличивают `d` из квадратичной формулы; если отбрасываете — экономите, но модель теряет ход своих рассуждений между шагами. Разумная политика: сохранять размышления только последнего шага, старые отбрасывать при компакции.

## 04.5 Что делать с потоковой выдачей

Потоковая передача не меняет цену: вы платите за все сгенерированные токены, даже если пользователь ушёл со страницы на середине ответа. Но она даёт два реальных рычага.

**Рычаг 1. Прерывание по сигналу пользователя.** Если пользователь закрыл вкладку или нажал «стоп», прерывайте запрос на сервере, а не только в интерфейсе. Иначе генерация продолжается и оплачивается полностью. Проверьте это в своём коде прямо сейчас: удивительно часто отмена доходит только до фронтенда.

**Рычаг 2. Ранняя остановка по содержимому.** В потоке видно начало ответа. Если модель начала писать не то (например, пошла в вежливое вступление вместо JSON), можно прервать и перезапросить с префиллом. Приём нишевый, но в высоконагруженных классификаторах экономит заметно.

Обратная сторона: потоковая выдача создаёт ощущение, что ответ «пишется бесплатно», и команды перестают следить за длиной. Метрика `out/in` должна быть на дашборде независимо от того, стримите вы или нет.

## 04.6 Как это ломается

| Симптом | Причина | Лечение |
|---|---|---|
| Доля `stop_reason: max_tokens` выше 1% | лимит режет полезные ответы | поднять лимит, сокращать длину форматом, а не обрезкой |
| Обрезанный JSON, ретраи | `max_tokens` меньше, чем нужно схеме | считать бюджет ответа по схеме, а не «на глаз» |
| Просили JSON, получили JSON внутри markdown-блока | нет префилла и нет структурированного вывода | префилл `{`, структурированный вывод по схеме |
| `out/in` упал, счёт не изменился | экономили на выходе там, где вход в 50 раз больше | смотреть на абсолютные деньги, а не на отношение |
| Размышления выключили — качество упало на сложных задачах | выключили глобально, а не по типу задачи | включать размышления по классу задачи, маршрутизация из [06](../06-model-selection/README.md) |
| Пользователь ушёл, а генерация продолжается | отмена не доходит до API | пробрасывать отмену на сервер и в клиент API |
| Ответы стали короткими и бесполезными | инструкция «максимально кратко» без указания, что обязательно должно быть | перечислить обязательные элементы ответа и ограничить остальное |

Последняя строка — самая частая ошибка этого модуля. «Отвечай максимально кратко» — плохая инструкция: модель начинает выбрасывать нужное. Хорошая инструкция всегда двухчастная: **что обязательно должно быть в ответе** и **что запрещено добавлять**.

## Упражнения

<details>
<summary><b>1.</b> Отношение `out/in` = 0,04, вход 30 000 токенов. Стоит ли заниматься выходом?</summary>

Нет. Выход — 1 200 токенов; при тарифе 3/15 $ это 0,018 $ против 0,09 $ за вход. Даже двукратное сокращение выхода даст 0,009 $, тогда как включение кэша на входе даст порядка 0,08 $. Идите в [модуль 01](../01-prompt-caching/README.md).

Смысл упражнения: **порядок рычагов зависит от профиля, а не от вкуса.** Сначала посчитайте, потом оптимизируйте.
</details>

<details>
<summary><b>2.</b> Классификатор обращений: 900 выходных токенов на обращение. Как довести до 50?</summary>

Формат: строгий JSON с полями `category`, `priority`, `escalate`, без пояснений. Префилл `{`, чтобы отсечь вступление. Структурированный вывод по схеме, чтобы формат был обязательным. Если объяснение нужно для аудита — поле `reason` с лимитом «не более 15 слов». `max_tokens` = 120 как страховка. Проверка: `pass_rate` на наборе тестов не изменился, а стоимость упала примерно в 15 раз.
</details>

<details>
<summary><b>3.</b> Почему `max_tokens  100` — плохой способ экономии для генерации текста?</summary>

Потому что это не сокращение, а обрезание на полуслове. Пользователь получает незаконченный ответ, ваш код — невалидный JSON, и в итоге вы платите за обрезанный ответ плюс за повторный запрос. `max_tokens` — предохранитель от аномалий; сокращать надо инструкцией и форматом, чтобы модель **сама** генерировала короче и заканчивала мысль.
</details>

<details>
<summary><b>4.</b> Агент делает 10 шагов. На каждом шаге модель пишет 150 токенов «размышлений вслух» в тексте ответа. Сколько это стоит?</summary>

Прямая стоимость: 1 500 выходных токенов. Но каждый такой абзац попадает в историю и переотправляется на всех последующих шагах: примерно 150 × (9+8+...+1) = 6 750 дополнительных входных токенов. При тарифе 3/15 $ это 0,0225 $ на выход плюс 0,02 $ на вход, то есть **вдвое дороже, чем кажется**. Отсюда правило: в агентном цикле промежуточные ответы модели должны быть максимально короткими — это экономит дважды.
</details>

<details>
<summary><b>5.</b> Как выбрать бюджет размышлений, не гадая?</summary>

Прогнать набор тестов на трёх–четырёх уровнях бюджета и построить кривую «`pass_rate` против `cost_per_task`». Выбрать точку начала плато. Затем разделить задачи на классы и назначить бюджет **по классу**: извлечению полей размышления не нужны вовсе, планированию нужны. Глобальная настройка почти всегда либо переплата на простых задачах, либо недобор качества на сложных.
</details>

## Чек-лист приёмки

- [ ] `out/in` считается по логам и есть на дашборде
- [ ] Для каждого типа запроса выставлен осознанный `max_tokens`
- [ ] Доля `stop_reason: max_tokens` меньше 1%
- [ ] Там, где ответ потребляет код, используется строгая схема, а не «попроси JSON»
- [ ] Применён префилл или структурированный вывод, чтобы отсечь вступления
- [ ] Инструкция по длине двухчастная: что обязательно и что запрещено
- [ ] Промежуточные ответы агента короткие (они множатся на число шагов)
- [ ] Бюджет размышлений выбран по кривой качество/цена и назначается по классу задачи
- [ ] Отмена запроса пользователем доходит до API, а не только до интерфейса
- [ ] Для правок кода и документов используется формат «дельта», а не «весь файл»

## Антиметрика модуля

**Средняя длина ответа.** Довести её до сорока токенов легко — достаточно запретить модели говорить полезное. Пара, которую надо смотреть: **`out/in` вместе с `pass_rate`** и, для продуктовых сценариев, вместе с долей случаев, когда пользователь нажал «подробнее» или переспросил. Рост переспрашиваний означает, что вы сэкономили на выходе и заплатили новым запросом — вдвое дороже.
