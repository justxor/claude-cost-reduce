## 1. Перед началом оптимизации

Если хотя бы один пункт не отмечен — оптимизировать рано, вы будете менять систему вслепую.

- [ ] Каждый вызов модели пишет `usage` и `cost_usd` в структурированный лог
- [ ] В логе есть `task_id`, `scenario`, `model`, `step`, `stop_reason`
- [ ] Стоимость задачи считается как сумма по `task_id`, включая провальные попытки
- [ ] Цены моделей вынесены в конфиг, указана дата актуальности
- [ ] Расчётная стоимость сверена с биллингом, расхождение меньше 10%
- [ ] Есть набор тестов минимум на 20 задач с эталонными ответами
- [ ] В наборе есть исторически провальные случаи и краевые условия
- [ ] Тесты проверены на чувствительность: искусственная поломка их роняет
- [ ] Измерен бейзлайн: `pass_rate`, `cost_per_task`, `cost_per_success`, `p50/p95` задержки
- [ ] Построено распределение стоимости задач, найден хвост p95/p99
- [ ] Известны три самых дорогих сценария по деньгам, а не по числу запросов
- [ ] Определён порог качества, ниже которого экономия неприемлема

## 2. Перед выкатом оптимизации в прод

- [ ] Изменение одно, а не пять сразу (иначе не поймёте, что сработало)
- [ ] Набор тестов прогнан до и после, обе цифры записаны
- [ ] `pass_rate` не ниже бейзлайна (или падение осознанно принято продуктом в письменном виде)
- [ ] `cost_per_success` посчитан, а не только `cost_per_request`
- [ ] Учтены ретраи, эскалации и ручная работа в стоимости
- [ ] Проверено, что расход не переехал: инфраструктура, эмбеддинги, ночные пайплайны
- [ ] Зонд кэша показывает `cache_write` только на первом запросе
- [ ] Есть тест на побайтовую стабильность собранного промпта
- [ ] Задержка p95 не выросла неприемлемо (актуально для каскадов)
- [ ] Есть флаг быстрого отключения оптимизации без деплоя
- [ ] Настроен алерт, который поймает деградацию этой оптимизации
- [ ] Результат записан в репозиторий: что сделали, цифры до/после, дата, версия набора тестов
- [ ] Обновлены соответствующие чек-листы и документация модуля

## 3. Скачок расходов: что делать в первые 20 минут

Runbook. Идти строго по порядку, не перескакивать.

- [ ] **0–2 мин.** Что деплоили за последние сутки? Совпадает ли начало скачка с релизом?
- [ ] **2–4 мин.** Больше задач или дороже задачи? (объём против `cost_per_task`)
- [ ] **4–6 мин.** Какой `scenario` вырос? Обычно виден один.
- [ ] **6–8 мин.** Кэш жив? `cache_read` упал, `cache_write` вырос — причина найдена.
- [ ] **8–10 мин.** `steps_per_task` вырос? Значит зацикливание.
- [ ] **10–12 мин.** Средний и p95 `input_tokens` выросли? Значит выросли данные, а не промпт.
- [ ] **12–14 мин.** Разбивка по `route_reason`: маршрутизация не поехала на дорогую модель?
- [ ] **14–16 мин.** Разбивка по `tenant_id`: это один клиент?
- [ ] **16–18 мин.** Принять меру: откат релиза, включение лимита, деградация, троттлинг клиента.
- [ ] **18–20 мин.** Зафиксировать: что произошло, что помогло, какой алерт или тест поймал бы это раньше.

**После инцидента (в тот же день):**

- [ ] Добавлен алерт или тест, который поймал бы это раньше
- [ ] Обновлён этот runbook, если порядок шагов оказался неоптимальным
- [ ] Посчитан ущерб в деньгах и записан в постмортем
- [ ] Проверено, нет ли такой же уязвимости в других сценариях

## 4. Ревью кода, который вызывает модель

Список для ревьюера. Каждый пункт — это реальная утечка, которую видели в проде.

**Промпт и кэш**
- [ ] Нет таймстемпов, `uuid`, случайных значений в верхней части промпта
- [ ] Словари сериализуются с сортировкой ключей
- [ ] Набор и порядок инструментов не зависят от текущего запроса
- [ ] Отметки кэша стоят на границах стабильных блоков

**Вход**
- [ ] Есть лимит на размер входа в токенах и понятная обработка превышения
- [ ] Результаты инструментов усечены по жёсткому лимиту с пометкой об усечении
- [ ] Инструменты возвращают сводки и идентификаторы, а не полные объекты
- [ ] У инструментов поиска есть `limit` по умолчанию
- [ ] Из результатов удалены служебные поля

**Выход**
- [ ] `max_tokens` выставлен осознанно, не «на всякий случай большой»
- [ ] Формат ответа задан схемой, если результат потребляет код
- [ ] Нет просьб «объясни подробно» там, где объяснение не используется
- [ ] Размышления включены только там, где нужны

**Цикл**
- [ ] Заданы бюджеты: шаги, токены, деньги, время
- [ ] Исчерпание бюджета возвращает частичный результат с `stop_reason`
- [ ] Есть детектор отсутствия прогресса
- [ ] Повторные вызовы инструментов с теми же аргументами обслуживаются кэшем
- [ ] Независимые вызовы инструментов идут параллельно в одном шаге
- [ ] Ретрай меняет условия, а не повторяет то же самое

**Учёт и безопасность**
- [ ] Вызов логирует `usage`, `cost_usd`, `task_id`, `scenario`
- [ ] В логи не попадают полные тексты промптов и ответов
- [ ] Ключи не в коде и не в URL
- [ ] В ключ кэша ответов входит версия промпта; персональные ответы не кэшируются в общем кэше

## 5. Недельный обзор расходов

Раз в неделю, 20 минут, желательно одним и тем же человеком.

- [ ] Расход за неделю против прошлой недели, в разбивке по `scenario`
- [ ] `cost_per_task` медиана и p95 — тренд
- [ ] `cost_per_success` — тренд, вместе с `pass_rate`
- [ ] `cache_hit_ratio` — не деградировал ли после релизов
- [ ] Топ-5 `tenant_id` по расходу; сравнение с их платежами
- [ ] Доля `stop_reason: budget` и `max_tokens`
- [ ] Доля ретраев и их успешность
- [ ] Список задач из хвоста p99: что это было и почему так дорого
- [ ] Сверка расчётной стоимости с биллингом
- [ ] Одна выбранная гипотеза оптимизации на следующую неделю — с ожидаемым эффектом в деньгах

**Правило обзора.** На выходе — одно решение, а не десять наблюдений. Оптимизация расходов работает как непрерывный процесс с маленькими шагами, а не как разовый проект.
